GOOD BOUNDARY

Extract a widget when the group has a meaningful name, repeats, deserves isolated testing, or makes its parent easier to understand. A helper method can shorten code, but a widget creates a real reusable component boundary.

STEP 4 · FINAL FIELDS

A widget configuration is a snapshot

Flutter may create a new widget when inputs change. The existing widget object does not mutate, so constructor-backed fields should be final.

Avoid mutable configuration
class CourseCard extends StatelessWidget {
  String title; // Mutable: avoid this.

  CourseCard({required this.title});
}
Prefer an immutable snapshot
class CourseCard extends StatelessWidget {
  const CourseCard({
    super.key,
    required this.title,
  });

  final String title;
}
Parent rebuilds

Its current data changes from “Flutter Layouts” to “Dart Async.”

→
New configuration

Flutter receives a new CourseCard(title: 'Dart Async').

STATE IS DIFFERENT

A stateless child can still display changing data. The state lives above it, and rebuilds supply a new immutable configuration. If a component truly owns changing UI state, use a stateful pattern deliberately.

STEP 6 · TYPED CALLBACKS

Callbacks can carry a value

VoidCallback says only “this happened.” Use a function type such as ValueChanged<String> when the child should also report which value was selected.

STEP 7 · CONSTANT CONSTRUCTORS

Make constant construction possible

When every instance field is final and initialization supports it, declare a const constructor. Callers can then create compile-time constant widgets when every argument is also constant.

Constant invocation
const ProgressBadge(
  progress: 0.72,
)

Both the constructor and argument support a compile-time constant.

Runtime invocation
CourseCard(
  title: course.title,
  onContinue: () => open(course),
)

The class may still have a const constructor, but these arguments are known at runtime.

Check a call site

✓ Use const: constructor and arguments are constant.
Constructor declaration

const CourseCard(...) makes constant instances possible; it does not force every call to be constant.

Constant context

Inside a const collection or constructor call, nested constant invocations do not need repeated const keywords.

WHY IT HELPS

Const communicates immutability and lets Dart canonicalize equal compile-time objects. Use it where valid, but never distort data flow merely to add the keyword.

STEP 9 · SHARED COMPONENTS

Give reusable widgets a predictable home

Move shared presentation components into lib/widgets/. Keep screen-owned state and orchestration in lib/screens/.

lib/
import 'package:flutter/material.dart';

import 'progress_badge.dart';

class CourseCard extends StatelessWidget {
  const CourseCard({
    super.key,
    required this.title,
    required this.lessonCount,
    required this.progress,
    required this.onContinue,
    this.onReview,
  });

  final String title;
  final int lessonCount;
  final double progress;
  final VoidCallback onContinue;
  final VoidCallback? onReview;

  @override
  Widget build(BuildContext context) {
    return Card(
      child: Padding(
        padding: const EdgeInsets.all(16),
        child: Column(
          crossAxisAlignment: CrossAxisAlignment.start,
          children: [
            Text(title, style: Theme.of(context).textTheme.titleLarge),
            Text('$lessonCount lessons'),
            const SizedBox(height: 16),
            ProgressBadge(progress: progress),
            const SizedBox(height: 16),
            Row(
              mainAxisAlignment: MainAxisAlignment.end,
              children: [
                if (onReview != null)
                  TextButton(onPressed: onReview, child: const Text('Review')),
                const SizedBox(width: 8),
                FilledButton(onPressed: onContinue, child: const Text('Continue')),
              ],
            ),
          ],
        ),
      ),
    );
  }
}
Import direction:

The screen imports shared widgets. course_card.dart imports progress_badge.dart. Shared presentation widgets do not import the dashboard screen or reach into its state.

Feature-first alternative

As an app grows, colocate a feature's screen and widgets under lib/features/courses/. The same dependency rule still applies.

Export only when useful

A barrel file can shorten imports, but direct imports are perfectly clear for a small project.

STEP 10 · PUT IT TOGETHER

Refactor the dashboard from the outside in

The screen keeps the course collection and changing message. Each list item configures a reusable card and connects its callbacks.

ListView.separated(
  padding: const EdgeInsets.all(16),
  itemCount: courses.length,
  separatorBuilder: (_, __) => const SizedBox(height: 12),
  itemBuilder: (context, index) {
    final course = courses[index];
    return CourseCard(
      title: course.title,
      lessonCount: course.lessonCount,
      progress: course.progress,
      onContinue: () => _openCourse(course),
      onReview: course.progress > 0
          ? () => _reviewCourse(course)
          : null,
    );
  },
)
Read the flow:

The dashboard maps domain data to widget parameters. The card renders that immutable configuration. A tap travels upward through a callback, and the dashboard updates state or navigates.

Show a practical extraction sequence
  1. Make the repeated card code work once.
  2. Name the complete visual unit and extract it.
  3. Replace hard-coded differences with typed constructor parameters.
  4. Move application behavior behind callbacks.
  5. Mark configuration fields final and add a const constructor when valid.
  6. Extract focused subcomponents only where they clarify responsibility.
  7. Move shared components into predictable files and update imports.
  8. Run the app after each small change.

Final challenge: reusable LessonTile

  1. Start with three repeated lesson rows containing an icon, title, duration, completion state, and action.
  2. Extract a LessonTile with required named parameters.
  3. Use ValueChanged<bool> to report completion changes.
  4. Use a nullable VoidCallback? to hide or disable an optional preview action deliberately.
  5. Add a const constructor and mark all configuration fields final.
  6. Compose a small CompletionBadge inside the tile.
  7. Move both shared widgets into lib/widgets/.
  8. Test long titles, zero duration, both completion states, and a missing preview callback.

Completion checklist

  • I extract widgets around meaningful responsibilities.
  • I pass changing data through typed constructor parameters.
  • I choose required, optional, and nullable inputs deliberately.
  • I keep widget configuration fields final.
  • I use VoidCallback for actions without a payload.
  • I use ValueChanged or a function type when an event carries data.
  • I understand const constructors and constant call sites.
  • I compose focused widgets without hiding ownership.
  • I organize shared components without creating circular dependencies.
