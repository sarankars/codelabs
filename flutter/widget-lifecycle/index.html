StatefulWidget Lifecycle
STEP 1 · BIG PICTURE

Follow a StatefulWidget from Birth to Removal

A StatefulWidget has a lifecycle. Flutter creates its State, initializes it, rebuilds its UI when needed, reacts to dependency and configuration changes, and finally cleans it up.

By the end: You can explain every major State lifecycle callback in an interview and practically use the callbacks that matter most in everyday Flutter.

OR

COURSE STRATEGY

We will recognize and explain all major callbacks, but our practical code will focus on createState(), initState(), build(), setState(), and dispose().

STEP 2 · TWO OBJECTS

StatefulWidget Is Not the State

The StatefulWidget is an immutable configuration. The separate State object stores changing data and survives ordinary rebuilds.

class CounterPage extends StatefulWidget {
  const CounterPage({super.key});

  @override
  State<CounterPage> createState() => _CounterPageState();
}

class _CounterPageState extends State<CounterPage> {
  int count = 0;

  @override
  Widget build(BuildContext context) {
    return Text('Count: $count');
  }
}
StatefulWidget

Immutable configuration supplied by the parent.

State

Mutable data and lifecycle callbacks associated with that widget.

STEP 3 · PRACTICAL

createState() and initState()

These are the beginning of the lifecycle. createState creates the State object; initState performs one-time initialization after that State is inserted into the tree.

CallbackWhenTypical use
createState()When Flutter needs the State objectReturn the State implementation
initState()Once for each State objectOne-time setup, controllers, subscriptions
@override
void initState() {
  super.initState();
  print('initState: runs once');
}
INTERVIEW POINT

initState() does not run every time build() runs.

STEP 4 · PRACTICAL

build() Can Run Many Times

build describes the current UI. setState tells Flutter that local State changed and schedules the State to rebuild; it does not recreate the State object.

@override
Widget build(BuildContext context) {
  print('build called');
  return ElevatedButton(
    onPressed: () {
      setState(() { count++; });
    },
    child: Text('Count: $count'),
  );
}
User presses button
↓
setState()
↓
State changes
↓
build() runs again
↓
Updated UI
Do not put one-time initialization, repeated API calls, or expensive side effects directly in build(). Flutter may call build many times.
STEP 5 · THEORY

didChangeDependencies()

Sometimes your widget uses information that comes from higher up in the widget tree. If that information changes, Flutter can call didChangeDependencies() so your widget can react to the new value.

@override
void didChangeDependencies() {
  super.didChangeDependencies();
  print('A dependency may have changed');
}

Think of it this way

Your widget may depend on something provided by a parent above it. For example, it may use the current app theme or the current screen size.

A value above this widget changes
↓
Flutter notices that this State depends on it
↓
didChangeDependencies()
↓
build() can run again using the new value

Common examples are values you read using Theme.of(context) and MediaQuery.of(context).

EASY RULE

initState() is mainly for one-time setup. didChangeDependencies() is for reacting when something your widget depends on from higher in the tree changes.

INTERVIEW POINT

Flutter calls didChangeDependencies() once after initState(). It may call it again later if a dependency used by this State changes.

STEP 6 · THEORY

didUpdateWidget()

A parent widget can rebuild and pass different values to the same StatefulWidget while Flutter keeps the existing State object. didUpdateWidget() lets the State compare the old values with the new values.

@override
void didUpdateWidget(covariant ProfilePage oldWidget) {
  super.didUpdateWidget(oldWidget);

  if (oldWidget.userId != widget.userId) {
    print('The userId changed');
  }
}
Parent rebuilds
↓
new widget configuration
↓
same State object
↓
didUpdateWidget(oldWidget)
↓
build()

oldWidget gives you the previous configuration; widget refers to the current configuration.

STEP 7 · PRACTICAL

deactivate() vs dispose()

deactivate means the State has been removed from its current place in the tree. dispose is the final cleanup callback when the State will not build again.

MethodMeaningFinal?
deactivate()Removed from the current tree position; it may still be reinserted.No
dispose()State is permanently removed and resources should be released.Yes
final controller = TextEditingController();
final focusNode = FocusNode();

@override
void dispose() {
  controller.dispose();
  focusNode.dispose();
  super.dispose();
}
RULE

Final cleanup belongs in dispose(), not normally in deactivate().

STEP 8 · THEORY

reassemble() and Hot Reload

reassemble is mainly a development-time lifecycle callback. Flutter uses it during reassembly, such as hot reload in development.

@override
void reassemble() {
  super.reassemble();
  print('reassemble');
}
ActionSimple mental model
Hot reloadInject changed code and generally preserve app State.
Hot restartRestart the Dart application and lose current app State.
Full restartRestart the application from the platform level.
Recognize, don't overuse: application code rarely needs to override reassemble().
STEP 9 · IMPORTANT PROPERTY

What Does mounted Mean?

mounted is not a lifecycle callback, but it tells you whether this State object is currently associated with the widget tree.

Future<void> loadData() async {
  await Future.delayed(const Duration(seconds: 2));

  if (!mounted) return;

  setState(() {
    loading = false;
  });
}
mounted == true

The State is associated with the tree.

mounted == false

The State is no longer mounted; do not call setState.

STEP 10 · PRACTICAL

Watch the Important Methods Run

Now combine the callbacks students will use most often and observe the console. Predict the output before running the app.

class LifecyclePage extends StatefulWidget {
  const LifecyclePage({super.key});

  @override
  State<LifecyclePage> createState() {
    print('1. createState');
    return _LifecyclePageState();
  }
}

class _LifecyclePageState extends State<LifecyclePage> {
  int count = 0;

  @override
  void initState() {
    super.initState();
    print('2. initState');
  }

  @override
  Widget build(BuildContext context) {
    print('3. build');
    return Scaffold(
      appBar: AppBar(title: const Text('Lifecycle Demo')),
      body: Center(
        child: ElevatedButton(
          onPressed: () => setState(() => count++),
          child: Text('Count: $count'),
        ),
      ),
    );
  }

  @override
  void dispose() {
    print('4. dispose');
    super.dispose();
  }
}

Experiment

  1. Open the screen and record the output.
  2. Press the button three times. Which method repeats?
  3. Remove the LifecycleDemo widget from its parent so it is permanently removed from the widget tree. Which callback runs?
  4. Add didChangeDependencies(), didUpdateWidget(), and deactivate() print statements and observe them when you later create suitable scenarios.
STEP 11 · REVISE

Know What Each Callback Means

You do not need to use every callback every day, but you should be able to recognize its purpose and explain when Flutter calls it.

Method / propertyInterview answer in one line
createState()Creates the State object for a StatefulWidget.
initState()One-time State initialization.
didChangeDependencies()Runs when something this State depends on from higher in the widget tree changes.
build()Describes the UI and may run many times.
setState()Marks local State as changed and schedules a rebuild.
didUpdateWidget()React to a new widget configuration while retaining State.
deactivate()State leaves its current tree location and may be reinserted.
dispose()Final cleanup before the State is permanently removed.
reassemble()Development-time reassembly callback, notably related to hot reload.
mountedWhether the State is currently associated with the tree.
