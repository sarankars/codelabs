STEP 4 · MODEL

Create Product

Use the typed model from the JSON parsing lesson.

class Product {
  final int id;
  final String title;
  final double price;
  final String? thumbnail;

  const Product({
    required this.id,
    required this.title,
    required this.price,
    this.thumbnail,
  });

  factory Product.fromJson(Map<String, dynamic> json) {
    return Product(
      id: json['id'] as int,
      title: json['title'] as String? ?? 'Untitled',
      price: (json['price'] as num? ?? 0).toDouble(),
      thumbnail: json['thumbnail'] as String?,
    );
  }
}
STEP 5 · SERVICE

Create ProductApiService

Networking code belongs in a service, not in widgets.

class ProductApiService {
  static const baseUrl = 'https://dummyjson.com';

  Future<List<Product>> fetchProducts() async {
    final response = await http.get(
      Uri.parse('$baseUrl/products?limit=20'),
    );

    if (response.statusCode != 200) {
      throw Exception('Failed to load products');
    }

    final data = jsonDecode(response.body) as Map<String, dynamic>;
    final list = data['products'] as List<dynamic>;

    return list
        .map((item) => Product.fromJson(item as Map<String, dynamic>))
        .toList();
  }
}
Rule:

The service returns Dart data or throws an exception. It never calls setState() or notifyListeners().

STEP 6 · REMOTE STATE

Create ProductProvider

The provider becomes the single source of truth for products and request state.

class ProductProvider extends ChangeNotifier {
  ProductProvider(this._service);

  final ProductApiService _service;

  List<Product> _products = [];
  bool _isLoading = false;
  bool _isMutating = false;
  String? _error;

  List<Product> get products => List.unmodifiable(_products);
  bool get isLoading => _isLoading;
  bool get isMutating => _isMutating;
  String? get error => _error;
}
STEP 7 · GET

Load Remote Data Through Provider

The provider controls loading, success, and failure around the service call.

Future<void> fetchProducts() async {
  _isLoading = true;
  _error = null;
  notifyListeners();

  try {
    _products = await _service.fetchProducts();
  } catch (e) {
    _error = e.toString();
  } finally {
    _isLoading = false;
    notifyListeners();
  }
}
loading=true → notifyListeners() → service GET → products/error → loading=false → notifyListeners()
STEP 8 · PROVIDE

Wrap the App with ChangeNotifierProvider

Create the provider above the screens that use it.

void main() {
  runApp(
    ChangeNotifierProvider(
      create: (_) => ProductProvider(
        ProductApiService(),
      )..fetchProducts(),
      child: const MyApp(),
    ),
  );
}
Notice:

..fetchProducts() starts the first request immediately after creating the provider.

STEP 10 · RENDER

Loading, Error, Empty, Success

Remote screens should deliberately handle all four states.

Widget buildBody(ProductProvider provider) {
  if (provider.isLoading && provider.products.isEmpty) {
    return const Center(child: CircularProgressIndicator());
  }

  if (provider.error != null && provider.products.isEmpty) {
    return Center(child: Text(provider.error!));
  }

  if (provider.products.isEmpty) {
    return const Center(child: Text('No products found'));
  }

  return ProductsList(products: provider.products);
}

STEP 13 · POST

Create Through Service and Provider

The service performs POST. The provider updates its local list and notifies the UI.

Future<Product> createProduct({
  required String title,
  required double price,
}) async {
  final response = await http.post(
    Uri.parse('$baseUrl/products/add'),
    headers: {'Content-Type': 'application/json'},
    body: jsonEncode({'title': title, 'price': price}),
  );

  if (response.statusCode != 201) {
    throw Exception('Failed to create product');
  }

  return Product.fromJson(
    jsonDecode(response.body) as Map<String, dynamic>,
  );
}
Future<bool> createProduct({
  required String title,
  required double price,
}) async {
  _isMutating = true;
  _error = null;
  notifyListeners();

  try {
    final product = await _service.createProduct(
      title: title,
      price: price,
    );
    _products = [product, ..._products];
    return true;
  } catch (e) {
    _error = e.toString();
    return false;
  } finally {
    _isMutating = false;
    notifyListeners();
  }
}
DummyJSON:

Writes are simulated, so the provider updates its own list to make the classroom app behave like a real CRUD app.

STEP 15 · PATCH + DELETE

Keep CRUD State in Provider

PATCH replaces the matching product. DELETE removes it from the list.

Future<bool> updateProduct(Product updated) async {
  _isMutating = true;
  notifyListeners();

  try {
    final saved = await _service.updateProduct(updated);
    final index = _products.indexWhere((p) => p.id == saved.id);
    if (index != -1) _products[index] = saved;
    return true;
  } catch (e) {
    _error = e.toString();
    return false;
  } finally {
    _isMutating = false;
    notifyListeners();
  }
}

Future<bool> deleteProduct(int id) async {
  _isMutating = true;
  notifyListeners();

  try {
    await _service.deleteProduct(id);
    _products.removeWhere((p) => p.id == id);
    return true;
  } catch (e) {
    _error = e.toString();
    return false;
  } finally {
    _isMutating = false;
    notifyListeners();
  }
}
STEP 16 · RESILIENCE

Keep Existing Data if Refresh Fails

A failed refresh should not necessarily erase products that were already useful.

First load fails

No cached products exist, so show the full error state with Retry.

Refresh fails

Keep the old products visible and show a SnackBar/banner explaining that refresh failed.

STATE DESIGN

Loading and error are not just booleans. Think about what data already exists when the event occurs.

STEP 18 · FINAL REVISION

Provider + REST API Revision

Finish the networking module with the key ideas.

Why a service class?
It isolates endpoints, HTTP methods, headers, JSON parsing, and response validation.
Why ChangeNotifier?
It owns changing application state and tells listening widgets when to rebuild.
watch vs read?
watch() subscribes and rebuilds; read() triggers actions without subscribing.
Why separate isLoading and isMutating?
Initial page loading and CRUD button operations are different UX states.
Why update locally with DummyJSON?
Its write endpoints are simulated and do not permanently alter the shared public dataset.
What is the final architecture?
Screen → Provider → Service → REST API, with typed Models shared between layers.
