STEP 1 · FOUNDATIONS

NoSQL Document Architecture

Understand how Cloud Firestore organizes real-time cloud data compared to traditional relational SQL databases.

By the end of this codelab: You will build real-time data-driven Flutter applications using Cloud Firestore, master Collections and Documents, perform CRUD operations, convert documents to/from custom Dart models with withConverter, run filtered queries, and stream real-time updates with StreamBuilder.

What is Cloud Firestore?

Cloud Firestore is Google's flexible, scalable, cloud-hosted NoSQL document database designed for mobile, web, and server development. It keeps your app's data in sync across client apps in real-time through listeners, while offering powerful offline data caching for iOS, Android, and Web.

🗃️ Document-Oriented NoSQL

Unlike relational SQL databases that store data in rigid tables with rows and columns, Firestore stores lightweight, JSON-like key-value structures called Documents organized inside Collections.

⚡ Real-Time & Offline First

Firestore uses persistent WebSocket and gRPC connections to push live database changes to connected clients instantly. If the device goes offline, local cache handles reads and writes seamlessly, syncing when reconnected.

SQL (Relational) vs. Firestore (NoSQL)

If you come from a SQL background (like SQLite, PostgreSQL, or MySQL), here is how concepts translate to Firestore:

Relational Concept (SQL)Cloud Firestore ConceptKey Differences
Database / Schema Firestore Database Firestore is schemaless — documents in the same collection don't need identical fields.
Table Collection A collection contains only documents; it cannot hold raw values directly.
Row / Record Document A set of key-value pairs (up to 1 MB). Each document has a unique ID within its collection.
Column Field Supports rich types including Strings, Numbers, Maps (nested objects), Arrays, and Timestamps.
JOIN clause Subcollection / Denormalization No JOIN operations! Queries are fast and shallow. Nested data is kept in subcollections or denormalized.

The Three Structural Pillars

Collection ("users") └── Document ("user_alex") ├── Field: name: "Alex Rivers" ├── Field: email: "alex@example.com" ├── Field: score: 450 └── Subcollection ("tasks") ├── Document ("task_001") │ ├── title: "Buy groceries" │ └── isDone: false └── Document ("task_002") ├── title: "Design Flutter UI" └── isDone: true
The Alternating Path Rule:

Firestore paths ALWAYS alternate: Collection / Document / Collection / Document. You can never have a collection inside a collection or a document directly inside a document without a collection separating them!

  • users → Collection Reference
  • users/alex123 → Document Reference
  • users/alex123/tasks → Collection Reference (Subcollection)
  • users/alex123/tasks/task456 → Document Reference

STEP 3 · CORE OBJECTS

CollectionReference & DocumentReference

Discover how Flutter interacts with Firestore paths through reference objects before executing read or write requests.

What is a Reference?

In Cloud Firestore, a Reference is simply a lightweight, local locator object that points to a specific path in your database. Creating a reference does NOT perform any network requests or allocate server resources.

CollectionReference

Points to a collection containing documents. Used to add new documents, query items, or listen to all documents in the collection.

FirebaseFirestore.instance.collection('tasks')
DocumentReference

Points to a single document inside a collection. Used to read, write, update, or delete that specific document.

FirebaseFirestore.instance.collection('tasks').doc('id123')

Obtaining the Firestore Singleton Instance

// Get the default Cloud Firestore instance
final FirebaseFirestore firestore = FirebaseFirestore.instance;

Auto-Generated IDs vs. Custom IDs

Firestore allows two ways to define document IDs:

1. Auto-Generated Document ID

Calling .doc() with no arguments generates a cryptographically random, collision-resistant 20-character string locally:

// Creates a reference with a generated ID (e.g. '7kF9mK2v0qP3zL8wY1tB')
final newDocRef = firestore.collection('tasks').doc();
print('Generated Document ID: ${newDocRef.id}');
2. Explicit / Custom Document ID

Passing an ID string specifies the exact document identifier. Perfect for linking user profiles to their Firebase Auth uid:

final currentUserId = 'auth_uid_12345';
// Points directly to /users/auth_uid_12345
final userDocRef = firestore.collection('users').doc(currentUserId);

Navigating Subcollections

To point to a subcollection, simply chain collection() and doc():

// Method A: Chained calls
final reviewsRef = firestore
    .collection('products')
    .doc('laptop_x1')
    .collection('reviews');

// Method B: Slash-separated path string
final reviewDocRef = firestore.doc('products/laptop_x1/reviews/rev_99');
RULE OF THUMB

Use collection.doc() when creating a reference with a custom ID or pre-generating an ID before writing. Use collection.add() when you want to write data and generate the ID in a single step.

STEP 4 · CRUD: CREATE

Writing & Adding Documents

Learn the different ways to write data to Firestore using add(), set(), and special FieldValue transformers.

1. Adding with Auto-Generated ID: collection.add()

The add() method creates a new document with an auto-generated ID and returns a DocumentReference pointing to the new document:

Future<void> addNewTask() async {
  final tasksCollection = FirebaseFirestore.instance.collection('tasks');

  try {
    DocumentReference docRef = await tasksCollection.add({
      'title': 'Install FlutterFire CLI',
      'description': 'Configure Flutter with Firebase tools',
      'isCompleted': false,
      'priority': 1,
      'createdAt': FieldValue.serverTimestamp(),
    });

    print('Task created successfully with ID: ${docRef.id}');
  } on FirebaseException catch (e) {
    print('Failed to add task: ${e.message} (code: ${e.code})');
  }
}

2. Writing with Custom ID: doc.set()

When you know the document ID in advance (e.g., storing a user profile under their Auth uid), use set():

Future<void> saveUserProfile({
  required String userId,
  required String name,
  required String email,
}) async {
  final userDoc = FirebaseFirestore.instance.collection('users').doc(userId);

  await userDoc.set({
    'name': name,
    'email': email,
    'role': 'student',
    'createdAt': FieldValue.serverTimestamp(),
  });
}

3. Beware of set() Overwriting vs. SetOptions(merge: true)

Danger: Default set() Overwrites!

If the document already exists, calling doc.set({'score': 100}) without merge options will completely delete and replace all existing fields in that document!

Safe Solution: SetOptions(merge: true)

Passing SetOptions(merge: true) preserves any unmentioned fields and only creates or updates the specific fields passed:

// Only updates 'score' or creates doc if missing;
// existing fields like 'name' and 'email' are preserved!
await userDoc.set(
  {'score': 100},
  SetOptions(merge: true),
);

4. Server-Side Atomic Operations with FieldValue

Firestore provides powerful atomic operators that evaluate directly on the server to prevent race conditions:

OperationSyntaxWhy Use It?
Server Timestamp FieldValue.serverTimestamp() Prevents client clock drift; guarantees the exact UTC time the server processed the write.
Atomic Increment FieldValue.increment(1) or FieldValue.increment(-5) Atomically updates numerical counters without reading current value first — immune to race conditions!
Array Union FieldValue.arrayUnion(['tag1', 'tag2']) Appends elements to an array field only if they do not already exist (set semantics).
Array Remove FieldValue.arrayRemove(['tag1']) Removes all occurrences of the specified elements from an array field. 
// Example: Increment views and add a tag atomically
await firestore.collection('articles').doc('flutter_tips').set({
  'viewCount': FieldValue.increment(1),
  'tags': FieldValue.arrayUnion(['flutter', 'dart']),
  'lastViewedAt': FieldValue.serverTimestamp(),
}, SetOptions(merge: true));
STEP 5 · CRUD: READ

Reading Documents & Collections

Fetch data on-demand using one-time asynchronous get() calls and extract field values safely.

1. Reading a Single Document: doc.get()

Calling get() on a DocumentReference returns a DocumentSnapshot. Always verify snapshot.exists before trying to access the data:

Future<void> fetchUserProfile(String userId) async {
  final docRef = FirebaseFirestore.instance.collection('users').doc(userId);

  try {
    final DocumentSnapshot snapshot = await docRef.get();

    if (snapshot.exists) {
      // Extract data map safely
      final data = snapshot.data() as Map<String, dynamic>;
      final name = data['name'] as String? ?? 'Anonymous';
      final email = data['email'] as String? ?? 'No email';
      print('User found: $name ($email)');
    } else {
      print('User document does not exist!');
    }
  } on FirebaseException catch (e) {
    print('Failed to read document: ${e.message}');
  }
}

2. Reading an Entire Collection: collection.get()

Calling get() on a CollectionReference returns a QuerySnapshot containing an iterable list of docs:

Future<void> fetchAllTasks() async {
  final querySnapshot = await FirebaseFirestore.instance
      .collection('tasks')
      .get();

  print('Total tasks retrieved: ${querySnapshot.size}');

  for (var docSnapshot in querySnapshot.docs) {
    final id = docSnapshot.id;
    final data = docSnapshot.data();
    print('Task [$id]: ${data['title']} (Completed: ${data['isCompleted']})');
  }
}

Controlling Cache vs. Server Source

By default, get() reads from the server and falls back to local cache if offline. You can control this behavior with GetOptions:

// Read exclusively from local device cache (0 cloud read cost!)
final cachedSnapshot = await docRef.get(
  const GetOptions(source: Source.cache),
);

// Force fetch from server, bypassing local cache
final serverSnapshot = await docRef.get(
  const GetOptions(source: Source.server),
);
When to use get()

Use get() for one-time checks: login profile load, checking if a username is available, or generating a static invoice/report.

When to use snapshots()

Use snapshots() (covered in Step 9) whenever the UI must react live to changes made by the user, teammates, or backend Cloud Functions.

STEP 6 · CRUD: UPDATE & DELETE

Updating & Deleting Documents

Modify existing records without overwriting other fields, perform nested map updates, and remove documents.

1. Updating Fields with doc.update()

The update() method modifies specific fields of an existing document without affecting any other fields:

Future<void> markTaskCompleted(String taskId) async {
  final docRef = FirebaseFirestore.instance.collection('tasks').doc(taskId);

  try {
    await docRef.update({
      'isCompleted': true,
      'completedAt': FieldValue.serverTimestamp(),
    });
    print('Task marked as completed!');
  } on FirebaseException catch (e) {
    if (e.code == 'not-found') {
      print('Cannot update: Document does not exist!');
    } else {
      print('Update error: ${e.message}');
    }
  }
}
Vital Distinction: update() vs. set()
  • update() fails with error code not-found if the document does not already exist.
  • set(..., SetOptions(merge: true)) will create the document if it doesn't exist, and merge fields if it does.

2. Updating Nested Maps with Dot Notation

Suppose your document has a nested map field: address: { city: "Pune", state: "MH" }. If you update it directly with {'address': {'city': 'Nagpur'}}, the state field will be lost!

To safely update nested keys without erasing siblings, use Dot Notation:

// Safe: Only modifies city, keeps state intact!
await firestore.collection('users').doc('user123').update({
  'address.city': 'Nagpur',
});

3. Deleting Specific Fields: FieldValue.delete()

To remove a field from a document entirely:

await docRef.update({
  'temporaryPromoCode': FieldValue.delete(),
});

4. Deleting a Document: doc.delete()

Future<void> deleteTask(String taskId) async {
  try {
    await FirebaseFirestore.instance.collection('tasks').doc(taskId).delete();
    print('Task deleted!');
  } on FirebaseException catch (e) {
    print('Delete failed: ${e.message}');
  }
}
SUBCOLLECTION ALERT

In Cloud Firestore, deleting a document does NOT delete its subcollections! Subcollections remain orphaned at their paths. If you want to delete subcollections, you must delete their documents explicitly or trigger a Cloud Function to clean them up.

STEP 7 · TYPE SAFETY

Custom Dart Models with withConverter

Eliminate brittle Map<String, dynamic> code and typos by converting Firestore documents into type-safe Dart classes.

Why Convert to Dart Models?

Without Models (Fragile):

Using raw maps means typing string keys repeatedly: doc['title']. A simple typo like doc['titel'] fails silently at runtime with null!

With Models (Type-Safe):

Get full IDE auto-completion, compile-time type checking, refactoring support, and clean null-safety guarantees: task.title.

1. Define the TaskModel Class

A complete Dart model with fromFirestore and toFirestore:

import 'package:cloud_firestore/cloud_firestore.dart';

class TaskModel {
  final String id;
  final String title;
  final String description;
  final bool isCompleted;
  final int priority; // 1 = Low, 2 = Medium, 3 = High
  final DateTime? dueDate;
  final DateTime createdAt;

  TaskModel({
    required this.id,
    required this.title,
    this.description = '',
    this.isCompleted = false,
    this.priority = 1,
    this.dueDate,
    DateTime? createdAt,
  }) : createdAt = createdAt ?? DateTime.now();

  // FACTORY: Convert Firestore DocumentSnapshot into TaskModel
  factory TaskModel.fromFirestore(
    DocumentSnapshot<Map<String, dynamic>> snapshot,
    SnapshotOptions? options,
  ) {
    final data = snapshot.data();
    return TaskModel(
      id: snapshot.id,
      title: data?['title'] as String? ?? 'Untitled',
      description: data?['description'] as String? ?? '',
      isCompleted: data?['isCompleted'] as bool? ?? false,
      priority: data?['priority'] as int? ?? 1,
      dueDate: (data?['dueDate'] as Timestamp?)?.toDate(),
      createdAt: (data?['createdAt'] as Timestamp?)?.toDate() ?? DateTime.now(),
    );
  }

  // METHOD: Convert TaskModel instance into Map for Firestore
  Map<String, dynamic> toFirestore() {
    return {
      'title': title,
      'description': description,
      'isCompleted': isCompleted,
      'priority': priority,
      if (dueDate != null) 'dueDate': Timestamp.fromDate(dueDate!),
      'createdAt': Timestamp.fromDate(createdAt),
    };
  }

  // Handy copyWith method for state updates
  TaskModel copyWith({
    String? title,
    String? description,
    bool? isCompleted,
    int? priority,
    DateTime? dueDate,
  }) {
    return TaskModel(
      id: id,
      title: title ?? this.title,
      description: description ?? this.description,
      isCompleted: isCompleted ?? this.isCompleted,
      priority: priority ?? this.priority,
      dueDate: dueDate ?? this.dueDate,
      createdAt: createdAt,
    );
  }
}

2. Connect with withConverter<T>()

Firestore offers the incredible withConverter<T>() method on collections and documents. It attaches serialization logic once, returning a strongly-typed CollectionReference<TaskModel>:

class TaskRepository {
  // Create a strongly-typed CollectionReference
  static final CollectionReference<TaskModel> tasksRef = FirebaseFirestore
      .instance
      .collection('tasks')
      .withConverter<TaskModel>(
        fromFirestore: TaskModel.fromFirestore,
        toFirestore: (TaskModel task, _) => task.toFirestore(),
      );

  // Type-safe ADD: Notice we pass a TaskModel object, not a Map!
  static Future<DocumentReference<TaskModel>> addTask(TaskModel task) async {
    return await tasksRef.add(task);
  }

  // Type-safe GET: Returns TaskModel directly!
  static Future<TaskModel?> getTask(String taskId) async {
    final docSnapshot = await tasksRef.doc(taskId).get();
    return docSnapshot.data(); // Returns TaskModel?
  }
}
Why withConverter is the Gold Standard:

When you use withConverter, all query operations, snapshots, and StreamBuilder snapshots automatically emit strongly typed TaskModel instances. You never have to manually map or cast JSON maps in your widgets again!

STEP 8 · QUERYING

Querying, Filtering & Sorting Records

Fetch exactly what you need using where(), orderBy(), limit(), and composite indexes.

1. Filtering with where()

Firestore lets you construct rich queries by chaining filter criteria:

OperatorExample CodeUse Case
isEqualTo .where('isCompleted', isEqualTo: false) Exact match
isNotEqualTo .where('status', isNotEqualTo: 'archived') Excluding values
isGreaterThan .where('priority', isGreaterThan: 1) Numeric / Date range
whereIn .where('category', whereIn: ['work', 'urgent']) Match any value in list (max 30 items)
arrayContains .where('tags', arrayContains: 'flutter') Checks if array field contains item
arrayContainsAny .where('tags', arrayContainsAny: ['dart', 'firebase']) Matches any tag in list (max 30 items)

2. Ordering and Limiting

// Query: Uncompleted tasks, sorted by priority (high to low), limited to 10
final Query<TaskModel> urgentTasksQuery = TaskRepository.tasksRef
    .where('isCompleted', isEqualTo: false)
    .orderBy('priority', descending: true)
    .limit(10);

3. Composite Queries & The Index Requirement

Understanding Composite Indexes:

Firestore queries are ultra-fast because every query uses an index. For simple queries (e.g. filtering by isCompleted only), Firestore creates single-field indexes automatically.

However, when you filter on one field and sort on another (or filter on multiple fields), Firestore requires a Composite Index.

What Happens When an Index is Missing?

If you run a query that requires an index that hasn't been built yet, Firestore will throw a FirebaseException with code failed-precondition and log a direct clickable URL in your debug console:

[cloud_firestore/failed-precondition] The query requires an index. You can create it here:
https://console.firebase.google.com/v1/r/project/codelab-demo/firestore/indexes?create_composite=...
PRO TIP

Click the link directly in your VS Code / Android Studio debug console! It opens the Firebase Console with the required fields pre-filled. Just click Create Index, wait 1-2 minutes for it to build, and re-run your app.

4. Pagination Basics with startAfterDocument

To implement "Load More" infinite scroll without reading all documents at once:

// Fetch the first page of 10 tasks
final firstPageSnapshot = await TaskRepository.tasksRef
    .orderBy('createdAt', descending: true)
    .limit(10)
    .get();

final lastVisibleDoc = firstPageSnapshot.docs.last;

// Fetch the next page of 10 tasks starting after the last item
final nextPageSnapshot = await TaskRepository.tasksRef
    .orderBy('createdAt', descending: true)
    .startAfterDocument(lastVisibleDoc)
    .limit(10)
    .get();
STEP 9 · REACTIVE UI

Real-Time Updates with StreamBuilder

Transform your Flutter interface into a live, reactive experience using snapshots() and StreamBuilder.

How Real-Time Snapshots Work

Instead of making one-off network requests with get(), calling snapshots() opens a persistent stream. Any time data is added, modified, or removed in the cloud (or by other users), Firestore pushes an updated snapshot down to your Flutter app automatically.

Device A updates Task #42 ↓ Cloud Firestore Database ↓ (Websocket / gRPC push) Device B receives snapshot & rebuilds StreamBuilder UI instantly!

The 4 Essential StreamBuilder States

When building with StreamBuilder, always gracefully handle all four UI states:

StateConditionRecommended UI
1. Loading snapshot.connectionState == ConnectionState.waiting CircularProgressIndicator() or Shimmer skeleton.
2. Error snapshot.hasError Error banner / message showing snapshot.error.
3. Empty !snapshot.hasData || snapshot.data!.docs.isEmpty Friendly empty state illustration or text: "No tasks yet!".
4. Active Data snapshot.hasData && snapshot.data!.docs.isNotEmpty ListView.builder displaying real-time records.

Clean StreamBuilder Implementation

class RealTimeTaskList extends StatelessWidget {
  const RealTimeTaskList({super.key});

  @override
  Widget build(BuildContext context) {
    // 1. Point to our type-safe query
    final Stream<QuerySnapshot<TaskModel>> taskStream = TaskRepository.tasksRef
        .orderBy('createdAt', descending: true)
        .snapshots();

    // 2. StreamBuilder subscribes and automatically unmounts listener on dispose
    return StreamBuilder<QuerySnapshot<TaskModel>>(
      stream: taskStream,
      builder: (context, snapshot) {
        // STATE 1: ERROR
        if (snapshot.hasError) {
          return Center(
            child: Text('Error loading tasks: ${snapshot.error}'),
          );
        }

        // STATE 2: LOADING INITIAL DATA
        if (snapshot.connectionState == ConnectionState.waiting) {
          return const Center(child: CircularProgressIndicator());
        }

        // STATE 3: EMPTY DATA
        final List<QueryDocumentSnapshot<TaskModel>> docs =
            snapshot.data?.docs ?? [];

        if (docs.isEmpty) {
          return const Center(
            child: Text(
              'No tasks found. Tap + to add one!',
              style: TextStyle(fontSize: 16, color: Colors.grey),
            ),
          );
        }

        // STATE 4: SUCCESS - RENDER REAL-TIME LIST
        return ListView.separated(
          itemCount: docs.length,
          separatorBuilder: (_, __) => const Divider(height: 1),
          itemBuilder: (context, index) {
            final TaskModel task = docs[index].data();

            return ListTile(
              leading: Checkbox(
                value: task.isCompleted,
                onChanged: (bool? value) {
                  // Toggle completed in Firestore
                  TaskRepository.tasksRef.doc(task.id).update({
                    'isCompleted': value ?? false,
                  });
                },
              ),
              title: Text(
                task.title,
                style: TextStyle(
                  decoration: task.isCompleted
                      ? TextDecoration.lineThrough
                      : null,
                ),
              ),
              subtitle: Text(task.description),
              trailing: IconButton(
                icon: const Icon(Icons.delete_outline, color: Colors.red),
                onPressed: () {
                  TaskRepository.tasksRef.doc(task.id).delete();
                },
              ),
            );
          },
        );
      },
    );
  }
}
No Manual setState() Needed:

StreamBuilder handles subscription lifecycle automatically. It calls setState() under the hood whenever new events arrive and cancels the stream subscription when the widget is disposed, preventing memory leaks!

class Task {
  final String id;
  final String title;
  final String description;
  final bool isCompleted;
  final int priority; // 1 = Low, 2 = Medium, 3 = High
  final DateTime createdAt;

  Task({
    required this.id,
    required this.title,
    this.description = '',
    this.isCompleted = false,
    this.priority = 1,
    DateTime? createdAt,
  }) : createdAt = createdAt ?? DateTime.now();

  factory Task.fromFirestore(
    DocumentSnapshot<Map<String, dynamic>> snapshot,
    SnapshotOptions? options,
  ) {
    final data = snapshot.data();
    return Task(
      id: snapshot.id,
      title: data?['title'] as String? ?? '',
      description: data?['description'] as String? ?? '',
      isCompleted: data?['isCompleted'] as bool? ?? false,
      priority: data?['priority'] as int? ?? 1,
      createdAt: (data?['createdAt'] as Timestamp?)?.toDate() ?? DateTime.now(),
    );
  }

  Map<String, dynamic> toFirestore() {
    return {
      'title': title,
      'description': description,
      'isCompleted': isCompleted,
      'priority': priority,
      'createdAt': Timestamp.fromDate(createdAt),

  }
}

// -------------------------------------------------------------
// 2. FIRESTORE SERVICE
// -------------------------------------------------------------
class FirestoreService {
  static final CollectionReference<Task> tasksRef = FirebaseFirestore
      .instance
      .collection('tasks')
      .withConverter<Task>(
        fromFirestore: Task.fromFirestore,
        toFirestore: (task, _) => task.toFirestore(),
      );

  // Stream with dynamic filter
  static Stream<QuerySnapshot<Task>> getTasksStream({String filter = 'all'}) {
    Query<Task> query = tasksRef.orderBy('createdAt', descending: true);

    if (filter == 'active') {
      query = query.where('isCompleted', isEqualTo: false);
    } else if (filter == 'completed') {
      query = query.where('isCompleted', isEqualTo: true);
    }

    return query.snapshots();
  }

  static Future<void> addTask(String title, String desc, int priority) async {
    await tasksRef.add(
      Task(id: '', title: title, description: desc, priority: priority),
    );
  }

  static Future<void> toggleTaskStatus(String id, bool currentStatus) async {
    await tasksRef.doc(id).update({'isCompleted': !currentStatus});
  }

  static Future<void> deleteTask(String id) async {
    await tasksRef.doc(id).delete();
  }
}

STEP 11 · ADVANCED WRITES

Batched Writes & Transactions

Execute atomic multi-document operations and prevent race conditions with transactions.

1. Batched Writes (Up to 500 Operations)

A Batched Write allows you to combine up to 500 set(), update(), and delete() operations into a single atomic request. Either all operations succeed, or none of them apply:

Future<void> markAllTasksCompleted(List<String> taskIds) async {
  final firestore = FirebaseFirestore.instance;
  // 1. Create a WriteBatch instance
  final WriteBatch batch = firestore.batch();

  // 2. Queue multiple update/set/delete operations
  for (final id in taskIds) {
    final docRef = firestore.collection('tasks').doc(id);
    batch.update(docRef, {
      'isCompleted': true,
      'updatedAt': FieldValue.serverTimestamp(),
    });
  }

  // 3. Commit the batch atomically
  try {
    await batch.commit();
    print('All tasks marked as completed in a single atomic batch!');
  } on FirebaseException catch (e) {
    print('Batch failed: ${e.message}');
  }
}

2. Transactions (Atomic Read-Then-Write)

Transactions are essential when a write operation depends on the current value of a document (e.g. transferring money, booking tickets, or adjusting stock inventory).

If another client modifies the document while the transaction is running, Firestore automatically retries the transaction to ensure mathematical consistency.

Future<void> transferFunds({
  required String senderId,
  required String recipientId,
  required double amount,
}) async {
  final firestore = FirebaseFirestore.instance;
  final senderRef = firestore.collection('accounts').doc(senderId);
  final recipientRef = firestore.collection('accounts').doc(recipientId);

  await firestore.runTransaction((Transaction transaction) async {
    // STEP 1: MUST PERFORM ALL READS FIRST
    final senderDoc = await transaction.get(senderRef);
    final recipientDoc = await transaction.get(recipientRef);

    if (!senderDoc.exists || !recipientDoc.exists) {
      throw Exception('One or both accounts do not exist!');
    }

    final double senderBalance = (senderDoc.data()?['balance'] as num).toDouble();
    if (senderBalance < amount) {
      throw Exception('Insufficient funds!');
    }

    final double recipientBalance = (recipientDoc.data()?['balance'] as num).toDouble();

    // STEP 2: PERFORM ALL WRITES
    transaction.update(senderRef, {'balance': senderBalance - amount});
    transaction.update(recipientRef, {'balance': recipientBalance + amount});
  });

  print('Funds transferred atomically!');
}
Golden Rule of Transactions:

In a Firestore transaction, all read operations must execute BEFORE any write operations! You cannot read a document after calling transaction.set() or transaction.update() within the same callback.

STEP 12 · PRODUCTION SECURITY

Firestore Security Rules

Protect your database on Google Cloud servers so malicious clients cannot tamper with or read private data.

Never Trust the Client:

Client-side Flutter code can be inspected, decompiled, or bypassed by attackers using custom HTTP requests. Security in Firebase is enforced strictly on the server through Firestore Security Rules.

Basic Structure of firestore.rules

Rules match document paths and allow or deny operations based on authentication status and request payload:

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // Helper functions
    function isAuthenticated() {
      return request.auth != null;
    }

    function isOwner(userId) {
      return request.auth != null && request.auth.uid == userId;
    }

    // 1. User Profiles: Anyone signed in can read, only the user can write
    match /users/{userId} {
      allow read: if isAuthenticated();
      allow write: if isOwner(userId);
    }

    // 2. Tasks: Only allow users to access their own tasks
    match /tasks/{taskId} {
      allow read, write: if isAuthenticated() &&
                            request.resource.data.userId == request.auth.uid;
      allow delete: if isAuthenticated() &&
                       resource.data.userId == request.auth.uid;
    }
  }
}

request.resource vs. resource

ObjectWhat It RepresentsTypical Use Case
request.auth Authentication token of the caller (uid, email, custom claims). Check if user is logged in (request.auth != null).
resource.data Data of the document as it currently exists on the server. Verify ownership before deleting or updating.
request.resource.data The incoming data being written to the database. Validate schema types, required fields, and values.

Schema Validation Example

// Ensure incoming task has a title of at least 3 characters and valid priority
match /tasks/{taskId} {
  allow create: if request.auth != null
    && request.resource.data.title is string
    && request.resource.data.title.size() >= 3
    && request.resource.data.priority in [1, 2, 3];
}

Revision & Knowledge Checklist

Review key takeaways and test your complete mastery of Cloud Firestore in Flutter.

What is the difference between a CollectionReference and a DocumentReference?
A CollectionReference points to a collection of documents (e.g. tasks) and is used for querying and adding items. A DocumentReference points to a single document within a collection (e.g. tasks/task_123) and is used to read, update, set, or delete that specific item.
Why use withConverter instead of raw Map<String, dynamic>?
withConverter transforms collections and documents into type-safe Dart classes with compile-time checks, IDE autocomplete, and centralized serialization. It prevents runtime typos (e.g. doc['titl'] returning null) and makes StreamBuilder code much cleaner.
Why use FieldValue.serverTimestamp() instead of DateTime.now()?
DateTime.now() uses the client device's clock, which can be wrong, set to a different timezone, or intentionally manipulated. FieldValue.serverTimestamp() guarantees the exact UTC time when Google Cloud servers processed the write.
What happens if a parent document is deleted when it has subcollections?
In Cloud Firestore, deleting a document does NOT delete its subcollections! Subcollections remain stored under their paths and must be deleted explicitly if desired.
