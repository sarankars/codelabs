STEP 1 · FOUNDATIONS

Introduction to Web Services

Discover what Web Services are, why distributed systems rely on them, the problems with legacy RPC/RMI, and the classic Web Service Architecture (Provider, Requester, Registry).

Target Outcome: Define Web Services according to the W3C standard, explain the 3 architectural roles (Publish, Find, Bind), and describe key characteristics for university exams.

1. What is a Web Service?

In distributed enterprise computing, different systems are implemented using diverse programming languages (Java, Python, C#, Node.js) and hosted on disparate operating systems (Linux, Windows, macOS). These systems need to exchange data seamlessly over local networks or the internet.

Official W3C Definition:

A Web Service is a software system designed to support interoperable machine-to-machine (M2M) interaction over a network. It has an interface described in a machine-processable format and communicates using standard internet protocols (typically HTTP) and structured message formats (XML or JSON).

2. Why Web Services? Legacy Distributed Computing Limitations

Before web services, distributed computing relied on technologies such as CORBA (Common Object Request Broker Architecture), DCOM (Distributed Component Object Model), and Java RMI (Remote Method Invocation). These had severe drawbacks:

Platform & Language Lock-in

Java RMI only worked between Java programs. DCOM was tightly bound to Microsoft Windows. Cross-language and cross-platform communication was extremely painful.

Firewall Blocking

Legacy RPC protocols used custom, dynamic network ports that corporate firewalls blocked by default. Web Services use standard HTTP port 80 and HTTPS port 443, effortlessly traversing firewalls.

Tight Coupling

Client and server had to share identical binary stubs and skeleton classes. Any minor method signature change broke all existing clients.

Heavyweight Binary Wire Formats

Data was encoded in proprietary binary streams rather than open, human-readable, self-describing text formats like JSON or XML.

3. Core Characteristics of Web Services

  • Interoperability: Any client (e.g. an iOS app written in Swift or a Python script) can talk to a Java backend.
  • Loose Coupling: The client and service are independent; the client only needs to know the service's contract or API specification.
  • Standard Communication Protocols: Relies on universally available protocols such as HTTP, HTTPS, TCP/IP.
  • Self-Describing Messages: Data payloads (JSON or XML) clearly define what each field means without requiring shared compiled code.
  • Synchronous & Asynchronous: Supports immediate request-response calls as well as long-running asynchronous notifications.

4. Web Services Architecture (The SOA Triangle)

The Service-Oriented Architecture (SOA) of web services is based on three primary roles and three fundamental operations:

FIND (Registers WSDL | | (Discovers URL or OpenAPI) | | & contract) | | +-----------------------+ +-----------------------+ | SERVICE PROVIDER | | SERVICE REQUESTER | | (Server hosting API) | | (Client/Consumer) | +-----------------------+ +-----------------------+ ^ | | | +---------------------+ 3. 2. Service Requester (Client)

STEP 2 · ARCHITECTURAL TYPES

Types of Web Services: SOAP vs. REST

Learn the two primary types of web services used in industry: contract-first SOAP (Simple Object Access Protocol) and resource-oriented REST (Representational State Transfer).

Target Outcome: Detail SOAP structure, define REST fundamentals, and construct a comprehensive head-to-head comparison table for exams.

1. The Two Dominant Web Service Types

In modern computing, web services are classified into two broad categories based on their design philosophy and protocol constraints:

1. SOAP (Simple Object Access Protocol)

A heavyweight, formal, standardized protocol governed by W3C. Exclusively uses XML for message formatting and enforces a strict contract defined by a WSDL (Web Services Description Language) file.

2. REST (Representational State Transfer)

A lightweight architectural style (not a protocol) governed by principles formulated by Roy Fielding. Treats everything as a Resource identified by a URI and uses standard HTTP methods.

2. Deep Dive: SOAP Web Services

SOAP relies on standard XML structures. Every SOAP message is an XML document composed of four distinct elements:

+====================================================================+ | <soap:Envelope> (Root element that defines the XML document) | | | | +--------------------------------------------------------------+ | | | <soap:Header> (Optional: Metadata like Authentication, | | | | WS-Security tokens, Transactions) | | | +--------------------------------------------------------------+ | | | | +--------------------------------------------------------------+ | | | <soap:Body> (Mandatory: Actual payload / RPC request) | | | | | | | | +----------------------------------------------------+ | | | | | <soap:Fault> (Optional: Error & Exception details | | | | | +----------------------------------------------------+ | | | +--------------------------------------------------------------+ | +====================================================================+ 
<!-- Example of a SOAP Request Message -->
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
    <soap:Header>
        <auth:Token>XYZ-12345</auth:Token>
    </soap:Header>
    <soap:Body>
        <m:GetStudentDetails xmlns:m="http://example.com/students">
            <m:StudentId>101</m:StudentId>
        </m:GetStudentDetails>
    </soap:Body>
</soap:Envelope>

Key Supporting Standards for SOAP (WS-* Stack):

  • WSDL (Web Services Description Language): An XML document that describes the service: available methods, parameter data types, return types, and endpoint URL.
  • UDDI (Universal Description, Discovery, and Integration): XML-based directory registry for publishing and finding SOAP services.
  • WS-Security: Enterprise-grade message-level security, encryption, and digital signatures.

3. Deep Dive: RESTful Web Services

REST stands for Representational State Transfer. Unlike SOAP, it is not a rigid protocol with strict XML wrappers. Instead, it leverages the native capabilities of the World Wide Web and HTTP protocol.

  • Resources: Every entity (Student, Course, Order) is a resource identified by a unique, logical URI (e.g., /api/students/101).
  • Representations: Resources can be represented in multiple formats, most commonly JSON (JavaScript Object Notation), but also XML, HTML, or plain text.
  • Standard Verbs: Uses HTTP methods (GET, POST, PUT, DELETE) as standard actions rather than custom remote procedure names.
// Example of a REST JSON Representation
{
    "id": 101,
    "name": "Aarav Sharma",
    "department": "Computer Science",
    "email": "aarav@example.com"
}

STEP 3 · REST PRINCIPLES

REST Architecture & HTTP Protocol

Explore Roy Fielding's 6 core architectural constraints of REST, HTTP verbs and their idempotency rules, and HTTP status codes.

Target Outcome: Explain the 6 architectural constraints of REST, classify HTTP methods as safe or idempotent, and map status codes to REST operations.

1. The 6 Architectural Constraints of REST

In his landmark 2000 doctoral dissertation, computer scientist Dr. Roy Fielding defined the 6 foundational constraints that an architecture must follow to be considered truly RESTful:

1. Client-Server Separation

Separates user interface concerns (Client) from data storage concerns (Server). Enhances portability of user interfaces across platforms (Web, iOS, Android) and allows independent evolution.

2. Statelessness (Stateless)

No client session context is stored on the server between requests. Every request from the client must contain all information (headers, authentication tokens, parameters) necessary for the server to process it.

3. Cacheability (Cacheable)

Responses must implicitly or explicitly define themselves as cacheable or non-cacheable. Well-managed caching eliminates client-server interactions, improving scalability.

4. Uniform Interface

The central differentiator of REST. All interactions follow a uniform contract via: Resource identification in URIs, Resource manipulation through representations, Self-descriptive messages, and HATEOAS.

5. Layered System

The client cannot tell whether it is connected directly to the end server or to an intermediary (proxy, cache, API gateway, load balancer). Improves system scalability and security.

6. Code on Demand (Optional)

Servers can temporarily extend client functionality by transferring executable code (e.g. JavaScript or compiled applets). This is the only optional constraint.

2. HTTP Verbs: Safe vs. Idempotent Methods

In RESTful design, remote operations are performed using standard HTTP methods. Two critical mathematical properties govern these methods for exams:

  • Safe Method: A method that does not modify any server-side resource state. It is strictly read-only (e.g. GET, HEAD).
  • Idempotent Method: Making the same request multiple times produces the exact same server state as making it once (e.g. GET, PUT, DELETE).
HTTP Verb CRUD Operation Safe? Idempotent? Typical URI Example
GET Read / Retrieve ✔ Yes ✔ Yes GET /api/students/101
POST Create / Insert ❌ No ❌ No POST /api/students
PUT Full Replace / Update ❌ No ✔ Yes PUT /api/students/101
PATCH Partial Modification ❌ No ❌ No (usually) PATCH /api/students/101
DELETE Remove ❌ No ✔ Yes DELETE /api/students/101
Why POST is NOT Idempotent:

If a client sends POST /api/students with body {"name":"John"} 5 times, the server creates 5 separate student records with 5 different IDs. Conversely, sending DELETE /api/students/101 5 times deletes record 101 on the first call and leaves it deleted for subsequent calls — the resource remains in the same state.

3xx Redirection 301 Moved Permanently, 304 Not Modified (Cache valid).
4xx Client Errors 400 Bad Request (Invalid JSON), 401 Unauthorized (Missing auth), 403 Forbidden, 404 Not Found.

STEP 4 · JAX-RS FRAMEWORK

Building RESTful Web Services with JAX-RS

Understand the JAX-RS specification, how the request dispatch pipeline works, and the core resource and HTTP method annotations.

Target Outcome: Explain the purpose of JAX-RS, list its major implementations, and utilize @Path, @GET, @POST, @Produces, and @Consumes in Java resources.

1. What is JAX-RS?

JAX-RS stands for Java API for RESTful Web Services (now standardized under the Jakarta RESTful Web Services umbrella). It is a standard Java specification (JSR 339, JSR 370) that provides a set of annotations and interfaces for building RESTful web services in Java.

Specification vs. Implementation:

Just as JPA is a specification implemented by Hibernate, JAX-RS is a specification that defines interfaces and annotations. Concrete runtime implementations include:

  • Jersey: The official reference implementation developed originally by Sun/Oracle.
  • RESTEasy: The JBoss / Red Hat implementation (standard in WildFly and Quarkus).
  • Apache CXF: An open-source enterprise services framework by Apache.

2. JAX-RS Request Lifecycle & Dispatcher Architecture

When an incoming HTTP request hits the web application container (e.g. Apache Tomcat), it passes through the JAX-RS pipeline:

CLIENT (Browser / Postman / Mobile) | Sends HTTP Request: GET /api/students/101 v +-------------------------------------------------------------------------------+ | SERVLET CONTAINER (Apache Tomcat / Jetty) | | * Routes URI matching '/api/*' to the JAX-RS Dispatcher Servlet. | +-------------------------------------------------------------------------------+ | v +-------------------------------------------------------------------------------+ | JAX-RS SERVLET DISPATCHER (org.glassfish.jersey.servlet.ServletContainer) | | | | 1. Resource Matching: Matches URI path against `@Path` annotations. | | 2. Method Matching: Matches HTTP verb (GET) against `@GET` annotation. | | 3. Parameter Binding: Extracts {id} via `@PathParam("id")`. | | 4. Content Negotiation: Checks 'Accept' header against `@Produces`. | | 5. Entity Providers: Serializes Java POJO ➔ JSON via Jackson/JSON-B. | +-------------------------------------------------------------------------------+ | v YOUR JAVA RESOURCE CLASS (@Path("/students")) ➔ Returns Student POJO | v (Converted to JSON by MessageBodyWriter) CLIENT receives: 200 OK with JSON Payload

3. Core JAX-RS Annotations

@Path

Identifies the URI path template to which the resource class or method responds (e.g. @Path("/students")).

HTTP Method Designators

@GET, @POST, @PUT, @DELETE, @HEAD, @OPTIONS map the Java method to corresponding HTTP verbs.

@Produces

Defines the MIME media types that the method can produce and return to the client (e.g. @Produces(MediaType.APPLICATION_JSON)).

@Consumes

Defines the MIME media types of payloads that the method can accept from the client in the request body (e.g. @Consumes(MediaType.APPLICATION_JSON)).

4. A Minimal JAX-RS Resource Class

package com.example.resource;

import com.example.model.Student;
import jakarta.ws.rs.*;
import jakarta.ws.rs.core.MediaType;
import java.util.Arrays;
import java.util.List;

@Path("/students") // Base URI: /api/students
@Produces(MediaType.APPLICATION_JSON)
@Consumes(MediaType.APPLICATION_JSON)
public class StudentResource {

    // Handles HTTP GET /api/students
    @GET
    public List<Student> getAllStudents() {
        return Arrays.asList(
            new Student(1, "Rohan Patel", "IT"),
            new Student(2, "Sneha Gupta", "Computer Science")
        );
    }

    // Handles HTTP POST /api/students
    @POST
    public String addStudent(Student student) {
        // Business logic to save student
        return "Student " + student.getName() + " registered successfully!";
    }
}

STEP 5 · ADVANCED JAX-RS

JAX-RS Parameters, Responses & Exception Mapping

Master parameter extraction annotations (@PathParam, @QueryParam, @HeaderParam, @FormParam), custom status codes with ResponseBuilder, and ExceptionMapper.

Target Outcome: Differentiate all parameter annotations, build customized HTTP responses with status codes, and write global exception mappers.

1. JAX-RS Parameter Binding Annotations

Clients send input to REST endpoints in multiple ways: inside the URI path, as query strings, in HTTP headers, or inside form bodies. JAX-RS provides dedicated annotations to extract these parameters:

1. @PathParam

Extracts values directly from the URI path template.
URI: /api/students/105
@GET @Path("/{id}")
public Student getStudent(@PathParam("id") int id)

2. @QueryParam

Extracts key-value query parameters appended to the URL after ?.
URI: /api/students?dept=CS&minGpa=3.5
public List<Student> filter(@QueryParam("dept") String dept)

3. @HeaderParam

Extracts values from the HTTP Request Headers.
Header: Authorization: Bearer token123
public Response auth(@HeaderParam("Authorization") String token)

4. @FormParam

Extracts HTML form input fields sent via POST with application/x-www-form-urlencoded.
public Response submit(@FormParam("username") String user)

5. @MatrixParam

Extracts matrix parameters separated by semicolons within a URI segment (e.g. /students/2026;semester=fall).

6. @CookieParam

Extracts cookie values sent by the client's web browser in the HTTP Cookie header.

2. The `Response` API and HTTP Status Codes

Instead of returning raw Java objects, robust enterprise APIs return the JAX-RS jakarta.ws.rs.core.Response object. This provides complete control over the HTTP status code, entity body, and response headers:

import jakarta.ws.rs.core.Response;
import jakarta.ws.rs.core.Response.Status;

// 1. Return 200 OK with Data
return Response.ok(student).build();

// 2. Return 201 Created with Location URI
URI location = URI.create("/api/students/" + newStudent.getId());
return Response.created(location).entity(newStudent).build();

// 3. Return 404 Not Found with custom error message
return Response.status(Status.NOT_FOUND)
               .entity("Student with ID " + id + " does not exist.")
               .build();

// 4. Return 204 No Content for successful deletion
return Response.noContent().build();

3. Global Error Handling with `ExceptionMapper`

In production web services, you should never allow unhandled Java stack traces to leak to the client. JAX-RS provides the ExceptionMapper<E> interface to intercept exceptions and translate them into friendly HTTP error responses:

package com.example.exception;

import jakarta.ws.rs.core.Response;
import jakarta.ws.rs.ext.ExceptionMapper;
import jakarta.ws.rs.ext.Provider;

@Provider // Marks class as a JAX-RS component extension
public class StudentNotFoundExceptionMapper implements ExceptionMapper<StudentNotFoundException> {

    @Override
    public Response toResponse(StudentNotFoundException exception) {
        ErrorMessage error = new ErrorMessage("STUDENT_NOT_FOUND", exception.getMessage(), 404);
        return Response.status(Response.Status.NOT_FOUND)
                       .entity(error)
                       .build();
    }
}

4. Complete CRUD REST Resource Example

package com.example.resource;

import com.example.model.Student;
import jakarta.ws.rs.*;
import jakarta.ws.rs.core.MediaType;
import jakarta.ws.rs.core.Response;
import java.util.*;

@Path("/students")
@Produces(MediaType.APPLICATION_JSON)
@Consumes(MediaType.APPLICATION_JSON)
public class FullStudentResource {

    // 1. GET ALL with optional query filtering
    @GET
    public Response getAllStudents(@QueryParam("dept") String department) {
        // Retrieve and return list
        return Response.ok(studentDatabase.getAll(department)).build();
    }

    // 2. GET BY ID using PathParam
    @GET
    @Path("/{id}")
    public Response getStudentById(@PathParam("id") int id) {
        Student s = studentDatabase.find(id);
        if (s == null) {
            return Response.status(Response.Status.NOT_FOUND).build();
        }
        return Response.ok(s).build();
    }

    // 3. CREATE via POST
    @POST
    public Response createStudent(Student student) {
        Student created = studentDatabase.save(student);
        return Response.status(Response.Status.CREATED).entity(created).build();
    }

    // 4. UPDATE via PUT
    @PUT
    @Path("/{id}")
    public Response updateStudent(@PathParam("id") int id, Student student) {
        Student updated = studentDatabase.update(id, student);
        return Response.ok(updated).build();
    }

    // 5. DELETE via DELETE
    @DELETE
    @Path("/{id}")
    public Response deleteStudent(@PathParam("id") int id) {
        studentDatabase.delete(id);
        return Response.noContent().build(); // 204 No Content
    }
}

Top 8 High-Yield 5-Marks University Questions

Question 1: Define Web Services and explain the SOA Architecture (Provider, Requester, Registry).

Model Answer (5 Marks):

Definition: A Web Service is a software system designed for interoperable machine-to-machine communication over a network using open standard protocols like HTTP, XML, and JSON.

  • Service Provider: The server that builds and deploys the web service. It performs the Publish operation to advertise its service in the Service Registry.
  • Service Registry: The central broker/directory (e.g., UDDI or API Gateway) where providers register service definitions and consumers search for available services.
  • Service Requester: The client application that requires functionality. It executes the Find operation on the Registry to retrieve the contract, and executes the Bind operation to invoke the Provider over HTTP.
Question 2: Compare SOAP and RESTful Web Services in detail (Provide at least 5 points).

Model Answer (5 Marks):

  • 1. Protocol vs Architectural Style: SOAP is a strict W3C protocol; REST is an architectural style based on HTTP principles.
  • 2. Message Formats: SOAP supports XML only; REST supports JSON, XML, Plain Text, HTML.
  • 3. Contract: SOAP enforces a strict WSDL contract; REST uses URI endpoints without requiring a formal contract.
  • 4. Caching: SOAP cannot be cached natively (sent via POST); REST GET responses are natively cacheable.
  • 5. Performance: SOAP is heavyweight due to XML envelope processing; REST is lightweight and faster.
Question 3: Explain the 6 architectural constraints of REST.

Model Answer (5 Marks):

  • 1. Client-Server: Separates UI concerns from data storage concerns.
  • 2. Statelessness: Every client request contains all data needed; server stores no session state.
  • 3. Cacheability: Responses must explicitly define whether they are cacheable.
  • 4. Uniform Interface: Consistent URI naming, standard HTTP verbs, and self-descriptive representations.
  • 5. Layered System: Client cannot tell if it connects to the end server or an intermediary proxy.
  • 6. Code on Demand (Optional): Server can deliver executable scripts (like JavaScript) to the client.
Question 4: Differentiate between Safe and Idempotent HTTP methods in RESTful Web Services.

Model Answer (5 Marks):

  • Safe Methods: Methods that do not modify server-side resource state (read-only). Examples: GET, HEAD. Calling them causes zero side effects.
  • Idempotent Methods: Methods where executing the request multiple times with identical parameters results in the exact same server state as executing it once. Examples: GET, PUT, DELETE.
  • Why POST is NOT Idempotent: Each POST call creates a new resource with a new identifier. Calling POST 5 times creates 5 new records.
Question 5: Explain the role of JAX-RS and list its popular implementations.

Model Answer (5 Marks):

JAX-RS (Java API for RESTful Web Services) is a standardized Jakarta EE specification that simplifies the creation of RESTful web services in Java using declarative annotations.

  • Specification Nature: JAX-RS defines interfaces and annotations (e.g. @Path, @GET, @Produces) without providing the runtime engine.
  • Implementations:
    • Jersey: The official reference implementation developed by Sun/Oracle.
    • RESTEasy: The Red Hat / JBoss implementation used in WildFly and Quarkus.
    • Apache CXF: An open-source enterprise services framework by Apache.

Question 7: How is exception handling implemented in JAX-RS using ExceptionMapper?

Model Answer (5 Marks):

ExceptionMapper<E> is a JAX-RS interface used to intercept unhandled application exceptions and convert them into standardized, clean HTTP error responses (e.g. 404 Not Found or 400 Bad Request).

@Provider
public class EntityNotFoundMapper implements ExceptionMapper<EntityNotFoundException> {
    @Override
    public Response toResponse(EntityNotFoundException ex) {
        return Response.status(Response.Status.NOT_FOUND)
                       .entity(new ErrorResponse("404", ex.getMessage()))
                       .type(MediaType.APPLICATION_JSON)
                       .build();
    }
}

The @Provider annotation automatically registers the mapper with the JAX-RS runtime.

Question 8: Write a complete JAX-RS Resource class demonstrating CRUD operations with proper HTTP verbs and status codes.

Model Answer (5 Marks):

@Path("/books")
@Produces(MediaType.APPLICATION_JSON)
@Consumes(MediaType.APPLICATION_JSON)
public class BookResource {
    @GET
    public Response getAll() { return Response.ok(bookService.findAll()).build(); }

    @GET @Path("/{id}")
    public Response getOne(@PathParam("id") int id) {
        Book b = bookService.find(id);
        return (b != null) ? Response.ok(b).build() : Response.status(404).build();
    }

    @POST
    public Response create(Book b) {
        Book created = bookService.save(b);
        return Response.status(Response.Status.CREATED).entity(created).build();
    }

    @PUT @Path("/{id}")
    public Response update(@PathParam("id") int id, Book b) {
        return Response.ok(bookService.update(id, b)).build();
    }

    @DELETE @Path("/{id}")
    public Response delete(@PathParam("id") int id) {
        bookService.delete(id);
        return Response.noContent().build(); // 204
    }
}
