Module IV · Database Foundations

Introduction to MongoDB & NoSQL

Understand document-oriented storage, schema flexibility, and how MongoDB differs fundamentally from relational DBMS.

What is MongoDB?

MongoDB is an open-source, high-performance, document-oriented NoSQL database designed for scalability, flexibility, and developer agility. Instead of storing data in rigid rows and columns like traditional relational databases (MySQL, Oracle, PostgreSQL), MongoDB stores records as flexible, self-describing BSON (Binary JSON) documents.

Architecture

Document-Oriented

Data is stored in JSON-like BSON documents. Fields can vary from document to document, enabling agile evolution without table alters.

Scalability

Horizontal Sharding

Distributes data across clusters of cheap commodity servers seamlessly to handle massive read/write traffic.

Reliability

Replica Sets

Provides high availability and automatic failover through primary-secondary replica replication sets.

Relational DBMS (RDBMS) vs. MongoDB (NoSQL)

Understanding the mapping between relational concepts and MongoDB equivalents is fundamental for university exams and real-world system architecture:

Feature / Concept Relational DBMS (SQL) MongoDB (NoSQL)
Data Model Tables composed of Rows and Columns Collections composed of BSON Documents
Schema Strict, pre-defined schema (DDL required) Dynamic, schema-less (fields vary per document)
Entity Record Tuple / Row / Record BSON Document (Key-Value pairs)
Primary Key Primary Key constraint (`PRIMARY KEY`) Unique default field: `_id` (ObjectId)
Relationship Strategy Foreign Keys with SQL JOINs Embedded sub-documents OR Document references (`$lookup`)
Scaling Vertical Scaling (Upgrade CPU/RAM) Horizontal Scaling (Sharding across distributed nodes)
Query Language Structured Query Language (SQL) MQL (MongoDB Query Language) / JSON expressions

JSON vs. BSON: Why MongoDB uses BSON internally

While developers write and view queries in human-readable JSON, MongoDB stores and transmits data over the wire as BSON (Binary JSON):

  • Traversability & Speed: BSON adds field length prefixes, allowing the database engine to skip unneeded fields rapidly during queries.
  • Rich Data Types: Standard JSON only supports strings, numbers, booleans, arrays, and null. BSON adds essential enterprise types such as Date, ObjectId, 64-bit Integer (long), Decimal128, and raw Binary data.
Q1. Explain the characteristics and architecture of MongoDB. Compare MongoDB with traditional Relational Database Management Systems (RDBMS). [5 Marks]
Definition & Characteristics: 1.5 M Comparison Table: 2.0 M BSON & ObjectId Concept: 1.5 M

1. Definition of MongoDB:

MongoDB is an open-source, document-oriented NoSQL database system that stores data in flexible, schema-free BSON (Binary JSON) format. Key characteristics include:

  • Schema Flexibility: Documents in the same collection do not need to share identical fields.
  • High Availability: Implemented using Replica Sets with automatic master failover.
  • Horizontal Scalability: Uses Sharding to distribute data across multiple physical machines.
  • Rich Query Language: Supports aggregation pipelines, text search, and geospatial indexing.

2. Tabular Comparison: RDBMS vs. MongoDB:

  • Structure: RDBMS uses Tables and Rows; MongoDB uses Collections and Documents.
  • Schema: RDBMS has a fixed schema; MongoDB is dynamic and schema-free.
  • Relationships: RDBMS relies on Foreign Keys and multi-table JOINs; MongoDB favors embedding sub-documents for fast atomic reads or manual references.
  • Transactions: RDBMS emphasizes ACID across normalized tables; MongoDB guarantees single-document atomicity and multi-document ACID transactions.

3. BSON & Primary Key `_id`:

Every MongoDB document requires a unique primary key in the _id field. If omitted, MongoDB automatically generates a 12-byte ObjectId composed of a 4-byte timestamp, 5-byte random value, and a 3-byte incrementing counter, ensuring global uniqueness across distributed systems.

Module IV · Application Connectivity

MongoDB Drivers & Client Architecture

Learn how application code bridges to MongoDB servers using official client libraries, connection pooling, and the wire protocol.

What is a MongoDB Driver?

A MongoDB Driver is an officially supported software client library that exposes an idiomatic programming language API (Java, Python, Node.js, C#, Go) to communicate with the MongoDB database cluster. It translates high-level application calls (such as inserting an object or executing a query) into MongoDB's binary Wire Protocol (OP_MSG over TCP/IP).

1. Application Code

Calls Java / JS methods (e.g. collection.insertOne(doc))

2. Driver Library

Serializes POJO/Object into BSON bytes

3. Wire Protocol

TCP/IP Socket stream on default port 27017

4. mongod Engine

WiredTiger storage engine writes to disk/memory

Key Responsibilities of a MongoDB Driver

1. Connection Pooling

Creating TCP connections is computationally expensive. Drivers maintain a warm pool of reusable connections (default 100 in Java) to eliminate handshake overhead on concurrent requests.

2. Replica Set Monitoring & SDAM

Server Discovery and Monitoring (SDAM): The driver continuously monitors replica set topology, automatically routing writes to the Primary and reads to Secondaries (if configured).

3. BSON Serialization

Converts native language objects (Java POJOs, Python dicts, JS objects) into binary BSON for storage, and deserializes BSON back into memory structures.

4. Authentication & TLS/SSL

Handles SCRAM-SHA-256 password handshakes, Kerberos, X.509 certificates, and TLS encrypted transport transparently.

Standard Connection String URI

All drivers parse the standardized MongoDB connection URI format:

Standard URI Format
mongodb://[username:password@]host1[:port1][,...hostN[:portN]][/[defaultauthdb][?options]]

// Example Local Development URI:
mongodb://localhost:27017/fsd_database

// Example Production Replica Set with Auth & TLS:
mongodb://admin:Secret123@node1.example.com:27017,node2.example.com:27017/fsd_db?replicaSet=rs0&ssl=true&authSource=admin
Q2. What is a MongoDB Driver? Explain the role of drivers in client-server communication and connection pooling with an example. [5 Marks]

1. Definition:

A MongoDB Driver is a language-specific client library (e.g., MongoDB Java Driver, PyMongo, Mongoose) providing an abstraction layer for application code to communicate with a MongoDB database instance over network sockets.

2. Core Functions of a Driver:

  • Wire Protocol Encoding: Translates native application objects (POJOs) into BSON binary wire packets using the standard OP_MSG protocol.
  • Connection Pooling: Maintains an internal cache of pre-established TCP connections. When a thread requires database access, it leases a connection from the pool and releases it upon completion, preventing server exhaustion.
  • Failover Handling: If a Primary replica fails, the driver discovers the newly elected Primary automatically without requiring an application restart.

3. Example in Java (Connecting to MongoDB):

Java Mongo Driver Snippet
// 1. Define Connection URI
String uri = "mongodb://localhost:27017";

// 2. Instantiate MongoClient (creates connection pool automatically)
try (MongoClient mongoClient = MongoClients.create(uri)) {
    // 3. Access Database and Collection
    MongoDatabase database = mongoClient.getDatabase("college_db");
    MongoCollection<Document> collection = database.getCollection("students");
    
    // 4. Perform database operation
    Document doc = new Document("name", "Alice").append("dept", "CSE");
    collection.insertOne(doc);
    System.out.println("Inserted successfully!");
}

Databases & Collections (Create & Drop)

Master the commands to switch databases, create collections, inspect metadata, and drop storage containers safely.

Dynamic Database Creation

Unlike SQL databases where you must execute CREATE DATABASE dbname; before inserting tables, MongoDB adopts a lazy / dynamic allocation strategy. When you switch to a database using use <dbname>, MongoDB creates the database in memory, but does not persist it to disk until the first document is inserted.

Database Operations

mongosh
// 1. Switch to (or create) database
use college_db

// 2. Show currently active database
db

// 3. List all persisted databases
show dbs

// 4. Drop current active database
db.dropDatabase()

Collection Operations

mongosh
// 1. Implicit collection creation
db.students.insertOne({ name: "Ravi", marks: 88 })

// 2. Explicit collection creation
db.createCollection("teachers")

// 3. List all collections in current DB
show collections

// 4. Drop an existing collection
db.students.drop()

Capped Collections

MongoDB allows creating Capped Collections: fixed-size, circular collections that automatically overwrite the oldest documents when allocated disk space is reached. They are ideal for high-throughput logging, telemetry, or cache buffers:

Capped Collection Example
// Creates a capped collection of max 5 MB and max 5000 documents
db.createCollection("system_logs", {
    capped: true,
    size: 5242880, // Size in bytes (5 MB)
    max: 5000      // Maximum number of documents
})

Module IV · Data Manipulation

CRUD Operations Deep Dive

Master Create, Read, Update, and Delete commands with comparison operators, projection, and update operators.

1. CREATE (Insert Documents)

MongoDB provides two primary insert methods: insertOne() and insertMany().

Insert Operations
// Insert a single document
db.students.insertOne({
    name: "Sneha Sharma",
    email: "sneha@gmail.com",
    department: "CSE",
    gpa: 8.9,
    skills: ["Java", "React", "MongoDB"],
    registeredAt: new Date()
});

// Insert multiple documents at once
db.students.insertMany([
    { name: "Rahul Verma", email: "rahul@gmail.com", department: "ECE", gpa: 7.8 },
    { name: "Pooja Nair", email: "pooja@gmail.com", department: "CSE", gpa: 9.2 }
]);

2. READ (Find & Query Documents)

Read operations use db.collection.find(query, projection). If query is {}, it matches all documents.

Query Operations & Operators
// 1. Find all students in CSE department
db.students.find({ department: "CSE" });

// 2. Comparison Operators: $gt (greater than), $gte, $lt, $lte, $in
db.students.find({ gpa: { $gte: 8.5 } });

// 3. Logical Operators: $and, $or
db.students.find({
    $or: [
        { department: "CSE" },
        { gpa: { $gt: 9.0 } }
    ]
});

// 4. Projection: Select only specific fields (1 = include, 0 = exclude)
// Suppress default _id and return only name and email
db.students.find({ department: "CSE" }, { name: 1, email: 1, _id: 0 });

// 5. Sorting, Skipping, and Pagination
db.students.find().sort({ gpa: -1 }).skip(0).limit(5); // -1 = DESC, 1 = ASC

3. UPDATE (Modify Documents)

Always use atomic update operators like $set, $inc, or $push. Without an operator, you risk replacing the entire document!

Update Operations
// 1. updateOne: Update a single document's GPA
db.students.updateOne(
    { email: "sneha@gmail.com" },             // Filter criteria
    { $set: { gpa: 9.1, status: "Active" } }   // Atomic update operator
);

// 2. updateMany: Increment semester by 1 for all CSE students
db.students.updateMany(
    { department: "CSE" },
    { $inc: { semester: 1 } }
);

// 3. Array modification with $push
db.students.updateOne(
    { email: "sneha@gmail.com" },
    { $push: { skills: "Docker" } }
);

// 4. Upsert (Update or Insert if document not found)
db.students.updateOne(
    { email: "vikram@gmail.com" },
    { $set: { name: "Vikram Rao", department: "IT" } },
    { upsert: true }
);

4. DELETE (Remove Documents)

Delete Operations
// Delete a single matching document
db.students.deleteOne({ email: "rahul@gmail.com" });

// Delete all documents matching condition
db.students.deleteMany({ status: "Inactive" });

// Remove all documents from a collection (leaves collection and indexes intact)
db.students.deleteMany({});

Form Validation & User Registration

Explore dual-layer validation strategy, regular expressions, and the end-to-end user registration pipeline.

The Dual-Layer Validation Strategy

A fundamental security law of Full Stack Engineering: Client-side validation enhances User Experience (UX), but Server-side validation guarantees Security.

Client-Side Validation (Browser)

  • Runs instantly in JavaScript without network latency.
  • Provides immediate visual feedback to the user (e.g. red borders, password strength meters).
  • Can be easily bypassed by attackers using Postman, cURL, or disabling JavaScript.

Server-Side Validation (Spring Boot)

  • Validates incoming JSON DTOs before touching service logic or database.
  • Protects against malicious payloads, SQL/NoSQL injection, and malformed inputs.
  • Mandatory & authoritative: Invalid requests are rejected with HTTP 400 Bad Request.

Client-Side Registration Logic (JavaScript)

register.js
const registerForm = document.getElementById("registerForm");

registerForm.addEventListener("submit", async (e) => {
    e.preventDefault(); // Stop standard page reload

    const username = document.getElementById("regUsername").value.trim();
    const email = document.getElementById("regEmail").value.trim();
    const password = document.getElementById("regPassword").value;

    // 1. Client-Side Regex Validation
    const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
    if (username.length < 4) {
        alert("Username must be at least 4 characters!");
        return;
    }
    if (!emailRegex.test(email)) {
        alert("Please enter a valid email address!");
        return;
    }
    if (password.length < 8) {
        alert("Password must be at least 8 characters long!");
        return;
    }

    // 2. Dispatch payload to Backend API
    try {
        const response = await fetch("http://localhost:8080/api/auth/register", {
            method: "POST",
            headers: { "Content-Type": "application/json" },
            body: JSON.stringify({ username, email, password })
        });

        const data = await response.json();
        if (response.ok) {
            alert("Registration successful! Please login.");
            window.location.href = "login.html";
        } else {
            alert("Registration failed: " + data.message);
        }
    } catch (err) {
        console.error("Network error:", err);
    }
});

Module IV · Application Security

Password Encryption & BCrypt Hashing

Learn why plain-text passwords must never be stored, how salt works, and how to configure BCryptPasswordEncoder.

Hashing vs. Encryption: Critical Distinction

Encryption (Two-Way)

Transforming plaintext into ciphertext using a secret key (e.g., AES-256). Reversible: anyone with the key can decrypt ciphertext back into the original password. Unsuitable for user passwords because a compromised key compromises all credentials.

Hashing (One-Way)

A mathematical one-way cryptographic function (e.g., SHA-256, BCrypt). Irreversible: it is computationally impossible to invert a hash back into the plain password. Passwords must ALWAYS be hashed.

Why BCrypt and Salting are Essential

Standard hashing algorithms like MD5 and SHA-256 are extremely fast, making them vulnerable to brute-force attacks and Rainbow Table lookups (pre-computed hash lookup tables).

  • Cryptographic Salt: A random 16-byte string generated per password and prepended before hashing. Even if two users choose "Password123", their resulting hashes are completely different, rendering rainbow tables useless.
  • Adaptive Work Factor (Cost): BCrypt includes a configurable cost parameter (default 10 = 210 iterations). As hardware becomes faster, developers can increase the cost to keep brute-force attacks computationally infeasible.

BCrypt Hash Structure

Deconstructing a BCrypt String
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
\__/ \/ \____________________/\_____________________________/
 |    |            |                         |
Algorithm Cost      22-character Salt         31-character Hash
($2a)     (10)     (Randomly generated)     (Result of hashing)

Spring Security BCrypt Implementation

SecurityConfig.java
@Configuration
public class SecurityConfig {

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder(); // Default cost factor = 10
    }
}

// In UserService.java:
@Service
public class UserService {
    @Autowired
    private UserRepository userRepository;
    @Autowired
    private PasswordEncoder passwordEncoder;

    public User registerUser(UserDTO dto) {
        User user = new User();
        user.setUsername(dto.getUsername());
        user.setEmail(dto.getEmail());
        
        // Hash password before saving to MongoDB
        String hashedPassword = passwordEncoder.encode(dto.getPassword());
        user.setPassword(hashedPassword);
        
        return userRepository.save(user);
    }
}

1. Password Hashing and Salting:

  • Hashing: A one-way cryptographic transformation that converts plain text into a fixed-length string. It cannot be mathematically reversed.

Login Functionality & Authentication

Understand authentication verification, session cookies vs. stateless JWT tokens, and token lifecycle management.

Authentication vs. Authorization

Authentication (AuthN)

"Who are you?" Verifying identity through credentials (e.g. comparing username and BCrypt password against the MongoDB database).

Authorization (AuthZ)

"What are you allowed to do?" Checking permissions or roles (e.g., ADMIN vs. USER) to access protected REST endpoints.

Stateful Sessions vs. Stateless JWT

Criteria Session-Based (Stateful) JWT-Based (Stateless)
Server State Server maintains session in memory/Redis Server is completely stateless (no session store)
Client Token Session ID stored in Cookie (JSESSIONID) Signed JWT token in LocalStorage / Cookie
Scalability Challenging across distributed server nodes Excellent for microservices & REST APIs
Header Format Automatic Cookie: JSESSIONID=... Explicit Authorization: Bearer <token>

1. Login Request

Client sends email & raw password

2. Fetch Document

3. BCrypt Match

encoder.matches(raw, hash) verifies password

4. Generate JWT

Server signs JWT with secret key and expiry

5. Client Storage

Frontend saves token and attaches to future API calls

  2. User Lookup: Spring Boot service queries MongoDB via userRepository.findByEmail(email). If absent, responds with HTTP 401 Unauthorized.
  3. Password Verification: Service verifies credentials using passwordEncoder.matches(loginDTO.getPassword(), user.getPassword()). If mismatch, responds with HTTP 401.
  4. Token Generation: Upon successful match, backend creates a cryptographically signed JSON Web Token (JWT) containing user claims (sub, role, exp).
  5. Response & Storage: Server returns HTTP 200 with the token. The browser saves it in localStorage or an HttpOnly cookie.

2. Structure of JWT Token:

A JWT consists of three Base64URL-encoded parts separated by dots:

  • Header: Algorithm and token type (e.g., {"alg": "HS256", "typ": "JWT"}).
  • Payload (Claims): User attributes and expiry (e.g., {"sub": "user@gmail.com", "role": "USER", "exp": 1730000000}).
  • Signature: Hash of Header + Payload using the server's private secret key, preventing tampering.

3. Client Authorization:

In subsequent authenticated requests, the client attaches the token in the HTTP header:

headers: { "Authorization": "Bearer " + token }

1. Spring Data MongoDB Overview:

Spring Data MongoDB provides an Object-Document Mapping (ODM) framework that simplifies building document-based applications. It removes low-level driver boilerplate and provides automated repository proxy generation.

2. Essential Annotations:

Connecting Backend with Frontend

What is CORS and Why Does It Occur?

CORS (Cross-Origin Resource Sharing) is a browser security mechanism enforced by the Same-Origin Policy. An origin is defined by the combination of Scheme + Domain + Port.

If your frontend is running on http://localhost:3000 or http://127.0.0.1:5500 and makes an HTTP request to Spring Boot running on http://localhost:8080, the browser will block the response with a CORS error unless the backend explicitly declares that the calling origin is allowed.

Enabling CORS in Spring Boot

Method 1: Controller-Level `@CrossOrigin`

StudentController.java
@RestController
@RequestMapping("/api/students")
@CrossOrigin(origins = "http://localhost:3000")
public class StudentController {
    // Endpoints...
}

Method 2: Global Configuration

WebConfig.java
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("http://localhost:3000", "http://127.0.0.1:5500")
                .allowedMethods("GET", "POST", "PUT", "DELETE")
                .allowedHeaders("*")
                .allowCredentials(true);
    }
}

Frontend Asynchronous Integration with `fetch()`

app.js (Fetching & Rendering Student List)
const API_URL = "http://localhost:8080/api/students";

// 1. Asynchronous GET Request
async function loadStudents() {
    try {
        const response = await fetch(API_URL, {
            method: "GET",
            headers: {
                "Accept": "application/json"
            }
        });

        if (!response.ok) {
            throw new Error(`HTTP error! status: ${response.status}`);
        }

        const students = await response.json();
        renderTable(students);
    } catch (error) {
        console.error("Failed to load students:", error);
    }
}

// 2. Render HTML Table dynamically
function renderTable(students) {
    const tableBody = document.getElementById("studentTableBody");
    tableBody.innerHTML = "";

    students.forEach(student => {
        const row = document.createElement("tr");
        row.innerHTML = `
            <td>${student.id}</td>
            <td>${student.name}</td>
            <td>${student.email}</td>
            <td>${student.department}</td>
            <td>${student.gpa}</td>
            <td>
                <button onclick="deleteStudent('${student.id}')">Delete</button>
            </td>
        `;
        tableBody.appendChild(row);
    });
}
Q11. What is CORS and why does it occur? Explain how frontend web applications communicate asynchronously with a Spring Boot REST backend using `fetch()` and JSON. [5 Marks]
CORS Explanation & Same-Origin Policy: 2.0 M Spring Boot Solution (@CrossOrigin / Config): 1.5 M Fetch API Implementation: 1.5 M

1. Definition of CORS:

Cross-Origin Resource Sharing (CORS) is a security protocol implemented by web browsers to restrict web pages from making AJAX requests to a different domain, port, or protocol than the one that served the web page (Same-Origin Policy). When a client application at http://localhost:3000 calls a backend at http://localhost:8080, the browser sends an HTTP OPTIONS pre-flight request. If the backend fails to respond with Access-Control-Allow-Origin, the browser blocks the response.

2. Resolving CORS in Spring Boot:

  • Annotating controllers with @CrossOrigin(origins = "http://localhost:3000").
  • Implementing a global WebMvcConfigurer bean overriding addCorsMappings() to allow specific origins, HTTP verbs (GET, POST, PUT, DELETE), and headers.

3. Asynchronous Communication using `fetch()`:

Modern frontend JavaScript uses the Promise-based fetch() API with async/await syntax:

  • Serializing payloads: body: JSON.stringify(data)
  • Setting content headers: headers: { 'Content-Type': 'application/json' }
  • Parsing responses: const result = await response.json();
