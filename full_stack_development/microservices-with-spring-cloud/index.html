STEP 1 · INTRODUCTION

The Shift to Microservices

Before we understand Spring Cloud, we need to understand the architectural shift from single-deployable monolithic applications to distributed systems.

By the end: You will understand what microservices are, why they introduce new architectural challenges, and how Spring Cloud acts as an ecosystem to solve them.

Architecture Comparison

Feature Monolith Microservices
Deployment One large file (e.g., a single .jar or .war). Dozens or hundreds of small, independent files.
Database Usually a single shared database. Ideally, each service owns its own database.
Scaling Scale the entire app by running multiple instances. Scale only the services that have high traffic.
Failure Impact A bug in one feature can crash the whole application. A bug in one service ideally isolates the failure.
The Trade-off

Microservices solve organizational and scaling problems, but they introduce heavy operational complexity. You are trading software complexity inside your code for network complexity between your servers.

STEP 2 · THE PROBLEM

The Challenges of Distributed Systems

When you split an application into 10 smaller applications, simple things suddenly become very hard.

Configuration Management

If a database password changes, do you manually update 10 different `application.properties` files and restart 10 servers?

Service Location

How does the "Order Service" know the IP address of the "Payment Service" if IPs change dynamically in the cloud?

Routing & Security

Do mobile clients need to memorize the IP and Port of every single microservice to fetch data?

Cascading Failures

If the Payment Service goes offline, will the Order Service crash waiting for a response, bringing down the whole system?

Enter Spring Cloud

Spring Cloud is an umbrella project. It provides a suite of tools designed specifically to solve these distributed systems problems using established design patterns.

STEP 3 · DISCOVERY

Service Discovery: Finding Other Services

We cannot hardcode IP addresses (like `http://192.168.1.15:8080`) when cloud servers dynamically spin up and down.

The Phonebook Analogy

Think of Service Discovery (e.g., Netflix Eureka) as a dynamic corporate phonebook.

  1. Registration: When a microservice starts up, it connects to the Eureka Server and says, "Hi, I am the PAYMENT-SERVICE, and I am currently at IP 10.0.0.5 on Port 8081."
  2. Heartbeats: The service pings Eureka every 30 seconds to prove it is still alive.
  3. Discovery: When the ORDER-SERVICE needs to call the payment service, it asks Eureka, "Where is PAYMENT-SERVICE?"
  4. Eureka replies with the live IP address.

STEP 4 · ROUTING

API Gateway: The Front Door

Without a gateway, a mobile app would have to make requests to 15 different servers on 15 different ports to load one user dashboard.

An API Gateway (e.g., Spring Cloud Gateway) acts as the single point of entry for all external clients (browsers, mobile apps).

Key Responsibilities:

  • Routing: Forwards `/api/orders/**` to the Order Service and `/api/users/**` to the User Service.
  • Cross-Cutting Concerns: Handles authentication, SSL termination, and CORS in one place.
  • Load Balancing: Works alongside Eureka to route traffic to the least busy instance of a service.

STEP 5 · CONFIGURATION

Centralized Configuration Server

Managing 50 different `application.properties` files across 50 servers is an operational nightmare.

Spring Cloud Config moves configuration files out of the application's source code and into a central repository (usually a private Git repository).

Git Repository (holds payment-prod.yml, order-prod.yml)
↓
Spring Cloud Config Server (Reads Git)
↓
Microservices (Fetch their config on startup)
Why Git?

By keeping configuration in Git, you get version control, audit logs (who changed the database password?), and easy rollbacks if a bad configuration brings down a service.

STEP 6 · RESILIENCE

Fault Tolerance & Circuit Breakers

In a distributed system, network failures and service crashes are guaranteed. We must design for failure.

The Cascading Failure

If Service A calls Service B, and Service B is incredibly slow (taking 30 seconds to reply), Service A will lock up all its threads waiting for a reply. Soon, Service A crashes too.

The Circuit Breaker Pattern (Resilience4j)

Modeled after an electrical circuit breaker, this pattern wraps network calls and monitors for failures.

State What happens?
Closed Everything is healthy. Traffic flows normally to the destination service.
Open Failures passed a threshold (e.g., 50% of requests failed). The circuit "trips." Network calls are blocked immediately and return a fallback (default) response to prevent cascading failure.
Half-Open After a timeout, the circuit lets a few requests through to test if the destination service has recovered. If yes, it closes. If no, it opens again.

STEP 8 · RECAP

Theoretical Revision

Review the core concepts before diving into the code in your next module.

What problem does Eureka solve?
It prevents hardcoding IP addresses by acting as a dynamic registry/phonebook for services to find each other.
What does an API Gateway do?
It acts as the single front door, handling routing, load balancing, and security before traffic hits individual microservices.
Why use a Spring Cloud Config Server?
To centralize configuration properties in a Git repository so they can be updated without rebuilding application code.
How does a Circuit Breaker prevent cascading failures?
If a downstream service is failing or slow, the circuit "opens" to block traffic and return fallback data immediately, freeing up server threads.
